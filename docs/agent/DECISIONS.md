# DECISIONS — decisiones de arquitectura (ADR breve)

> Agregar al final. Formato: ID · fecha · decisión · motivo. No reabrir una decisión sin motivo nuevo.

- **ADR-001 · 2026-11-09 · Stack** Django + DRF + PostgreSQL / React + Vite + TS. Motivo: modelo muy relacional, roles, archivos, reportes; front desacoplado que consume API REST.
- **ADR-002 · Monorepo** `backend/` y `frontend/` en un solo repo. Motivo: 2 desarrolladores, cambios coordinados front/back.
- **ADR-003 · Arquitectura por capas** views → serializers → services/selectors → models. Motivo: SOLID, RNF010 (modularidad), pruebas unitarias sin DB.
- **ADR-004 · Autenticación** JWT (SimpleJWT) + permisos por rol en backend. Motivo: RNF001, SPA desacoplada.
- **ADR-005 · Auditoría** `django-simple-history` para cambios de datos + tabla de eventos de acceso/exportación. Motivo: RNF008.
- **ADR-006 · Alertas** comando de gestión diario (cron) al inicio; Celery solo si se necesita. Motivo: simplicidad.
- **ADR-007 · Agente sin escritura en git** El agente no hace add/commit/push; propone el commit. Motivo: control del historial por el usuario.
- **ADR-008 · Pruebas en 3 niveles** unit / integration / system con marcadores. Motivo: las de sistema no siempre se pueden ejecutar.
- **ADR-009 · Nombres de dominio en español** igual que el diccionario de datos; campos en snake_case. Motivo: trazabilidad con el MER en la sustentación.
- **ADR-010 · 2026-11-09 · Sin Docker** Stack ejecutado local: PostgreSQL 18 instalado, Python 3.13.13 con venv, Node v24.15.0 LTS. Motivo: preferencia explícita del usuario (T-001 revisada).
- **ADR-011 · 2026-11-09 · MFA con TOTP** pyotp (6 dígitos, 30s, ventana ±1 paso). Secreto guardado cifrado con Fernet (`cryptography`). Códigos de recuperación (10) hasheados con el hasher de Django. mfa_token: `TimestampSigner` de Django (5 min, propósito validado). Access token en body; refresh en cookie HttpOnly SameSite=Lax. Motivo: seguridad según T-001 revisada.
- **ADR-012 · 2026-11-12 · Contraseña temporal y cambio obligatorio (T-002)** Creación/reset de contraseña por admin genera temporal del sistema (mostrada una sola vez), marca `debe_cambiar_password=True`, limpia bloqueo y revoca refresh tokens. El login devuelve `password_change_required` + token de propósito `password_change` (5 min, un solo uso) y exige cambio antes de continuar a MFA/sesión. **Tras inactivar un usuario, el access token se rechaza de inmediato**; tras reset de contraseña/MFA el access token ya emitido puede vivir hasta su expiración (≤15 min) mientras el refresh queda revocado. Motivo: control de acceso y recuperación administrativa segura (RF002/RNF001).
- **ADR-013 · 2026-11-12 · Auditoría en app dedicada y semántica de eventos (T-002)** `RegistroAuditoria` vive en app `auditoria` (sin JSON, 3FN) con `AccionAuditoria` explícita; eventos de sesión y gestión de usuarios se registran vía `registrar_evento`. `LOGIN_EXITOSO` se registra solo al emitir sesión final (no en pasos intermedios). `LOGIN_FALLIDO`/`MFA_RECHAZADO` se persisten antes de lanzar el error (fuera de atomic que revierta). IP por `REMOTE_ADDR` salvo `TRUST_X_FORWARDED_FOR=True`. Motivo: trazabilidad RNF008 consistente y consultable.
- **ADR-015 · 2026-11-23 · Activo sin ubicación (T-004)** `Activo` no guarda sede/ubicación. La ubicación efectiva se deriva de la asignación del responsable (T-005), que aporta `Usuario.sede`. Guardarla en Activo sería dato derivado (violación 3FN). `Ubicacion` queda sin uso por ahora (deuda), no se borra. Motivo: normalización 3FN y RNF010.
- **ADR-016 · 2026-11-24 · Situación derivada y evidencia inmutable, sin cron (T-006a)** La situación del mantenimiento preventivo (`PENDIENTE`, `VENCIDO`, `INCUMPLIDO`, `COMPLETADO`, `CANCELADO`) **no se almacena**: se deriva en el selector a partir de `estado`, `fecha_programada` y la existencia de una reprogramación (`reprogramacion_de` OneToOne self), usando `timezone.localdate()` en el backend. No hay cron ni proceso que "marque vencidos": el KPI mensual consulta la situación en el momento. Reprogramar un `PENDIENTE` mueve el mismo registro (200); reprogramar un `VENCIDO` crea un registro nuevo con `reprogramacion_de` y el original queda como evidencia `INCUMPLIDO` (201), sin borrarse, por lo que pesa en el KPI como incumplido. Un `INCUMPLIDO` es inmutable: no se completa, cancela ni reprograma de nuevo. Motivo: evitar jobs/estado duplicado (3FN), trazabilidad de incumplimientos y KPI verificable.
- **ADR-017 · 2026-11-24 · Correctivo como registro simple (T-006a)** Un correctivo se guarda con `tipo=CORRECTIVO`, `fecha_programada` = fecha del evento, `observacion` = qué pasó y `fecha_seguimiento`; nace `COMPLETADO` (soporte ya dado) y no participa del calendario ni del KPI preventivo (`resumen`/`calendario` filtran `tipo=PREVENTIVO`). Se registra por `POST /api/v1/mantenimientos/correctivos/`; la lista usa el listado estándar con `?tipo=CORRECTIVO`. Motivo: el flujo correctivo es informativo y no requiere reprogramación/evidencia; evitar mezclar métricas preventivas.
- **ADR-018 · 2026-11-24 · Dashboard agregado por rol (T-011 parcial)** El tablero consume un único `GET /api/v1/dashboard/resumen/` que agrega en `selectors.py` inventario, cumplimiento preventivo y costos (sin guardar estado derivado). Admin y técnico reciben el bloque de mantenimiento, vencidos y valores; el usuario responsable solo recibe inventario (sin mantenimientos ni montos). Motivo: una sola llamada por pantalla, consultas optimizadas, y no exponer información de mantenimiento/costos a quien no la opera.
- **ADR-019 · 2026-11-24 · Licencias como control operativo, sin Excel (T-007 parcial)** El módulo reemplaza el Excel de control de licencias (uso interno, no plantilla de importación/exportación). `Licencia` guarda `proveedor` FK + `servicio` (no se crea tabla `Software`: el Excel describe servicios como dominios, hosting o internet, y `LicenciaActivo` queda para cuando se asocien equipos). El proveedor se crea/reactiva implícitamente al guardar la licencia usando el nombre normalizado, sin pantalla de catálogo propia (se gestiona en admin). `dias_para_renovacion` y `estado_renovacion` (VIGENTE/POR_VENCER ≤30 días/VENCIDA/INACTIVA) se derivan, no se almacenan. Las licencias son solo ADMINISTRADOR (RF009). Motivo: 3FN con menos tablas innecesarias, cero datos derivados y una UX de captura rápida; garantías quedan para una segunda fase.
- **ADR-020 · 2026-11-24 · Asignaciones como fuente del responsable (T-005)** `AsignacionActivo` es la relación activo↔colaborador con `fecha_inicio`/`fecha_fin` e histórico; una constraint parcial garantiza **una sola asignación abierta** por activo. El estado del activo se sincroniza en la misma transacción: asignar → `ASIGNADO`, devolver → `DISPONIBLE`; `cambiar_estado` rechaza `ASIGNADO` para obligar a pasar por el flujo. Solo ADMINISTRADOR escribe (RF005); ADMINISTRADOR y TÉCNICO leen la trazabilidad (RF012). Reasignar cierra la anterior en la misma fecha de inicio de la nueva y abre otra, conservando todo el historial. `MovimientoActivo` (ubicaciones/movimientos) queda pendiente: la pregunta "quién ha tenido este equipo" se responde con el historial de asignaciones y el detalle del activo. El seed regulariza los activos que el seed de inventario dejó en `ASIGNADO` sin relación.
